## 1. 任务目标（必须满足）

实现一个基于 C 语言的**简化状态机框架**，并基于该框架实现一个**仪器运行状态机示例**。

本任务必须同时包含两部分：

### 1.1 状态机框架

实现一个最小可用的事件驱动状态机框架，支持：

- 状态对象
- 事件分发
- 状态切换
- 进入/退出日志
- 上下文对象维护当前状态

### 1.2 示例状态机

基于框架实现一个仪器运行状态机，包含：

- 待机状态
- 运行状态
- 报警状态
- 调试状态

用来证明：

- 同一个事件在不同状态下行为不同
- 行为由状态对象决定
- 不是通过 `if(state == ...)` 或大 `switch-case` 实现

------

## 2. 设计目标（必须体现）

本示例必须明确体现状态模式，而不是普通状态枚举判断。

必须体现：

- 状态被抽象为对象
- 上下文对象只持有“当前状态”
- 事件统一通过分发函数送入当前状态
- 当前状态对象负责决定如何处理事件
- 状态切换通过统一接口完成
- 不允许在主流程中用 `if/else` 或大 `switch` 判断当前状态后再执行动作

------

## 3. 框架范围（必须严格限制）

本示例只实现一个**极简事件驱动状态机框架**。

只允许实现以下内容：

- 状态接口
- 状态上下文
- 事件枚举
- 状态分发
- 状态切换
- 状态进入/退出日志

不允许扩展为完整 QP 类框架。

### 明确禁止：

- 事件队列
- 多线程
- Active Object
- 分层状态机（HSM）
- 定时器事件
- 历史状态
- 状态嵌套
- 复杂消息系统

说明：

> 本示例仅借鉴 QP 一类事件驱动状态机的“状态对象 + 事件分发 + 状态切换”思想，不实现完整框架能力。

------

## 4. 框架核心抽象（必须存在）

------

### 4.1 事件类型

必须定义统一事件枚举：

```c
typedef enum
{
    EVENT_START = 0,
    EVENT_STOP,
    EVENT_ALARM_ON,
    EVENT_ALARM_CLEAR,
    EVENT_ENTER_DEBUG,
    EVENT_EXIT_DEBUG
} event_t;
```

说明：

- 所有状态都通过这些事件响应外部输入
- 不允许每个状态使用不同事件接口

------

### 4.2 状态对象接口

必须定义抽象状态结构体：

```c
typedef struct state
{
    const char *name;
    void (*on_enter)(struct state *self, struct state_context *ctx);
    void (*on_exit)(struct state *self, struct state_context *ctx);
    void (*handle_event)(struct state *self, struct state_context *ctx, event_t event);
} state_t;
```

说明：

- `name`：状态名称，用于日志
- `on_enter`：进入状态时调用
- `on_exit`：退出状态时调用
- `handle_event`：处理事件

------

### 4.3 状态机上下文

必须定义状态机上下文对象：

```c
typedef struct state_context
{
    state_t *current_state;
} state_context_t;
```

说明：

- 上下文只保存“当前状态”
- 不允许在上下文中再保存一个 `enum current_state`
- 当前状态的语义必须由 `current_state` 指针体现

------

## 5. 框架接口（必须提供）

必须至少提供以下接口：

```c
void state_machine_init(state_context_t *ctx, state_t *init_state);
void state_machine_dispatch(state_context_t *ctx, event_t event);
void state_machine_transition(state_context_t *ctx, state_t *target_state);
const char *event_to_string(event_t event);
```

语义要求：

### 5.1 `state_machine_init`

- 设置初始状态
- 调用初始状态的 `on_enter`

### 5.2 `state_machine_dispatch`

- 打印当前事件和当前状态
- 将事件交给 `current_state->handle_event`

### 5.3 `state_machine_transition`

- 调用旧状态 `on_exit`
- 切换到目标状态
- 调用新状态 `on_enter`
- 打印状态切换日志

### 5.4 `event_to_string`

- 将事件枚举转换成字符串
- 用于日志输出

------

## 6. 状态处理原则（必须遵守）

状态处理必须遵循以下原则：

### 6.1 同一事件在不同状态中可有不同处理

例如 `EVENT_START`：

- 在 `IDLE` 中：启动运行，切换到 `RUNNING`
- 在 `RUNNING` 中：忽略
- 在 `ALARM` 中：拒绝
- 在 `DEBUG` 中：拒绝

### 6.2 状态自己决定行为

不允许框架或主函数判断：

```c
if (ctx->current_state == &idle_state) ...
```

必须由状态对象自己的 `handle_event` 决定。

### 6.3 状态切换必须通过统一接口

禁止在状态处理函数中直接写：

```c
ctx->current_state = &running_state;
```

必须调用：

```c
state_machine_transition(ctx, &running_state);
```

## 7. 示例状态机定义（必须实现）

基于框架实现一个“仪器运行状态机”。

必须存在以下状态对象：

- `idle_state`
- `running_state`
- `alarm_state`
- `debug_state`

每个状态必须是独立模块或独立实现，不允许所有状态逻辑堆在一个函数里。

## 8. 状态语义要求（必须严格实现）

------

### 8.1 IDLE 状态

状态含义：

- 仪器待机
- 未运行
- 未报警
- 非调试

必须支持以下事件：

#### `EVENT_START`

- 打印启动日志
- 切换到 `RUNNING`

#### `EVENT_ENTER_DEBUG`

- 打印进入调试日志
- 切换到 `DEBUG`

#### `EVENT_ALARM_ON`

- 打印报警触发日志
- 切换到 `ALARM`

#### `EVENT_STOP`

- 忽略，打印日志说明“already idle”

#### `EVENT_ALARM_CLEAR`

- 忽略，打印日志说明“no alarm”

#### `EVENT_EXIT_DEBUG`

- 忽略，打印日志说明“not in debug”

------

### 8.2 RUNNING 状态

状态含义：

- 仪器正在运行

必须支持以下事件：

#### `EVENT_STOP`

- 打印停止运行日志
- 切换到 `IDLE`

#### `EVENT_ALARM_ON`

- 打印运行中报警日志
- 切换到 `ALARM`

#### `EVENT_START`

- 忽略，打印日志说明“already running”

#### `EVENT_ENTER_DEBUG`

- 拒绝，打印日志说明“cannot enter debug while running”

#### `EVENT_ALARM_CLEAR`

- 忽略，打印日志说明“no alarm in running state”

#### `EVENT_EXIT_DEBUG`

- 忽略

------

### 8.3 ALARM 状态

状态含义：

- 仪器处于报警状态
- 不允许运行
- 不允许进入调试

必须支持以下事件：

#### `EVENT_ALARM_CLEAR`

- 打印报警解除日志
- 切换到 `IDLE`

#### `EVENT_START`

- 拒绝，打印日志说明“cannot start while alarm active”

#### `EVENT_STOP`

- 忽略，打印日志说明“already stopped by alarm”

#### `EVENT_ENTER_DEBUG`

- 拒绝，打印日志说明“cannot enter debug while alarm active”

#### `EVENT_ALARM_ON`

- 忽略，打印日志说明“alarm already active”

#### `EVENT_EXIT_DEBUG`

- 忽略

------

### 8.4 DEBUG 状态

状态含义：

- 仪器处于调试模式
- 不允许进入正常运行

必须支持以下事件：

#### `EVENT_EXIT_DEBUG`

- 打印退出调试日志
- 切换到 `IDLE`

#### `EVENT_ALARM_ON`

- 打印调试中报警日志
- 切换到 `ALARM`

#### `EVENT_START`

- 拒绝，打印日志说明“cannot start while in debug mode”

#### `EVENT_ENTER_DEBUG`

- 忽略，打印日志说明“already in debug mode”

#### `EVENT_STOP`

- 忽略，打印日志说明“not running in debug mode”

#### `EVENT_ALARM_CLEAR`

- 忽略

------

```text
[State] enter IDLE
[State] exit IDLE
[State] enter RUNNING
```

- 即使进入/退出逻辑很简单，也必须实现
- 用于体现状态对象的生命周期行为

## 10. 日志输出要求（必须有）

必须通过日志清楚体现：

- 当前收到的事件
- 当前由哪个状态处理
- 是否发生状态切换
- 进入/退出哪个状态
- 对不合法事件的处理结果

建议输出风格：

```text
[FSM] init -> IDLE
[State] enter IDLE

[FSM] event START in state IDLE
[IdleState] handle START
[FSM] transition: IDLE -> RUNNING
[State] exit IDLE
[State] enter RUNNING
```

对于非法事件：

```text
[FSM] event START in state RUNNING
[RunningState] already running, ignore START
```

## 13. 禁止事项（非常重要）

AI 生成代码时必须避免以下问题：

### 13.1 禁止用状态枚举 + 大 switch 实现全部逻辑

错误示例：

```c
switch (ctx->state_enum)
{
    case IDLE:
        ...
        break;
    case RUNNING:
        ...
        break;
}
```

这不是本示例要表达的状态模式。

------

### 13.2 禁止在 main 中判断当前状态再决定行为

错误示例：

```c
if (ctx.current_state == &idle_state) ...
```

------

### 13.3 禁止省略状态对象

必须有独立的状态对象，而不是只定义几个函数名。

------

### 13.4 禁止直接修改 current_state

状态切换必须统一通过：

```c
state_machine_transition(...)
```

------

### 13.5 禁止把所有状态处理都写在一个文件的大函数中

每个状态至少应有独立实现，或者清晰拆分。

## 15. 推荐结构体设计（可直接采用）

```c
typedef enum
{
    EVENT_START = 0,
    EVENT_STOP,
    EVENT_ALARM_ON,
    EVENT_ALARM_CLEAR,
    EVENT_ENTER_DEBUG,
    EVENT_EXIT_DEBUG
} event_t;

typedef struct state_context state_context_t;
typedef struct state state_t;

struct state
{
    const char *name;
    void (*on_enter)(state_t *self, state_context_t *ctx);
    void (*on_exit)(state_t *self, state_context_t *ctx);
    void (*handle_event)(state_t *self, state_context_t *ctx, event_t event);
};

struct state_context
{
    state_t *current_state;
};
```
