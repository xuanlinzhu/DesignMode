1. ## 1. 目标

   实现一个具备以下能力的框架：

   - **Bus（总线）**
     - 维护设备列表与驱动列表
     - 提供 `match()` 规则，并触发 `probe()`
     - 可选提供互斥锁（共享物理总线需要）
     - 对共享物理总线（如 SPI）提供统一总线操作入口：`ops->configure()` 与 `ops->xfer()`
   - **Device（设备）**
     - 表示**硬件实例**（如 `spi1.0`、`spi1.1`、`uart1`）
     - 通过 `compatible` 描述“我是谁”（简化设备树）
     - 通过 `cfg` 提供实例参数（CS/mode/max_hz 或 base/irq 等）
     - 通过 `driver_data` 保存实例私有上下文（等价 RTT `user_data` / Linux `drvdata`）
   - **Driver（驱动）**
     - 表示某类设备的驱动代码
     - 通过 `compatible` 声明支持的设备类型
     - 提供 `probe()`：作为工厂方法，完成实例初始化并绑定 `device->ops`
   - **Factory Method（工厂方法）**
     - `driver->probe(device)`
     - 在匹配成功后执行：分配私有数据、绑定 ops、完成必要初始化

   示例场景：

   - **SPI 案例**：一个 `spi_bus` 下挂 2 个 SPI 设备（不同 CS），体现“共享总线互斥 + 统一入口 xfer”
   - **UART 案例**：UART 设备挂在 `platform_bus`（逻辑总线），体现 Linux “所有设备归属某条 bus”

   ------

   ## 2. 角色映射（GoF ↔ 驱动框架）

   | GoF 工厂方法角色              | 本示例中的实体                                               |
   | ----------------------------- | ------------------------------------------------------------ |
   | Product（抽象产品）           | `device_t`（统一设备抽象）                                   |
   | ConcreteProduct（具体产品）   | `spi_flash dev` / `spi_lcd dev` / `uart dev`（probe 后绑定 ops + driver_data） |
   | Creator（抽象创建者）         | `bus_t`（组织 device/driver + match）                        |
   | ConcreteCreator（具体创建者） | `spi_bus`、`platform_bus`（同属 bus_t 实例）                 |
   | Factory Method                | `driver_t::probe(device_t*)`                                 |

   ## 3. 核心数据结构（最小集合，按讨论结果定版）

   ### 3.1 设备操作接口（Linux 风格 read/write）

   - `read(dev, buf, n)` / `write(dev, buf, n)` 返回 `ssize_t`
   - device 层是抽象；具体实现由 probe 绑定的 `ops` 决定

   ```
   typedef struct dev_ops {
       int     (*open)(void *dev);
       int     (*close)(void *dev);
       ssize_t (*read)(void *dev, void *buf, size_t n);
       ssize_t (*write)(void *dev, const void *buf, size_t n);
       int     (*ioctl)(void *dev, unsigned long cmd, void *arg);
   } dev_ops_t;
   ```

   ### 3.2 device_t（抽象产品 + 实例描述）

   ```
   typedef struct device {
       const char      *name;        // "spi1.0" / "uart1"
       const char      *compatible;  // "acme,spi-flash" / "acme,uart"
       struct bus      *bus;         // 指向 spi_bus / platform_bus
       const dev_ops_t *ops;         // probe 后绑定
       void            *driver_data; // RTT user_data / Linux drvdata：实例私有上下文
       void            *cfg;         // 设备描述/参数（CS、mode、base、irq等）
   } device_t;
   ```

   > 说明：**CS/base/irq 等绝不进入通用 device_t 字段**，全部放入 `cfg` 或 `driver_data`。

   ------

   ## 3.3 bus_t（简化 Linux bus_type + 共享总线入口）

   ### bus_ops_t（仅对“共享物理总线”有意义）

   ```
   typedef int (*bus_configure_fn)(struct bus *bus, struct device *dev);
   typedef int (*bus_xfer_fn)(struct bus *bus,
                              struct device *dev,
                              const void *tx,
                              void *rx,
                              size_t len);
   
   typedef struct bus_ops {
       bus_configure_fn configure; // 可选：切换设备/参数时配置控制器
       bus_xfer_fn      xfer;      // 统一传输入口：负责锁 + CS + 控制器访问
   } bus_ops_t;
   ```

   ### bus_t

   ```
   typedef struct bus {
       const char *name;              // "spi" / "platform"
       bus_match_fn match;            // match(dev, drv)
   
       device_t  *devices[MAX_BUS_DEVICES];
       size_t     device_count;
   
       driver_t  *drivers[MAX_BUS_DRIVERS];
       size_t     driver_count;
   
       simple_mutex_t lock;           // 共享物理总线互斥
       bool has_lock;                 // spi_bus=true, platform_bus=false
   
       const bus_ops_t *ops;          // spi_bus 有，platform_bus 通常为 NULL
       void *bus_data;                // 控制器实例上下文（如 SPI1 寄存器/HAL句柄）
   } bus_t;
   ```

   ### 设计原则（关键点）

   1. **bus 是组织者 + 匹配者**
      - 维护 devices/drivers
      - match 成功后触发 probe
   2. **共享物理总线的“互斥 + 事务”收敛到 bus->ops**
      - 锁在 `bus->ops->xfer()` 内部
      - driver 不直接访问控制器硬件，避免绕过锁
   3. **platform_bus 是“逻辑总线容器”**
      - 不代表共享物理介质
      - 一般 `has_lock = false`, `ops = NULL`

   ------

   ## 3.4 driver_t（工厂方法提供者）

   ```
   typedef struct driver {
       const char *name;         // "spi_flash" / "uart"
       const char *compatible;   // 支持的设备类型标识
       struct bus *bus;          // spi_bus / platform_bus
       int (*probe)(device_t *dev); // ⭐ 工厂方法
   } driver_t;
   ```

   `probe(dev)` 责任：

   1. 解析 `dev->cfg`
   2. 分配/填充 `dev->driver_data`
   3. 绑定 `dev->ops`
   4. 必要的硬件/资源初始化（可简化为模拟）

   ------

   ## 4. 匹配与创建流程（核心）

   ### 4.1 注册 driver（Linux 风格）

   `bus_register_driver(bus, drv)`：

   1. 把 `drv` 放入 `bus->drivers[]`
   2. 遍历 `bus->devices[]`，对每个 `dev` 执行 `bus->match(dev, drv)`
   3. 匹配成功 → 调用 `drv->probe(dev)`（工厂方法）

   ### 4.2 注册 device（Linux 风格）

   `bus_register_device(bus, dev)`：

   1. `dev->bus = bus`，加入 `bus->devices[]`
   2. 遍历 `bus->drivers[]`，对每个 `drv` 执行 `bus->match(dev, drv)`
   3. 匹配成功 → `drv->probe(dev)`（工厂方法）

   > 所以 **device 先注册 / driver 先注册** 都能工作（体现 Linux “动态匹配”思想）。

   ## 5. 三个驱动实例（对比性强）

   ### 5.1 SPI 总线：一个 bus 下两个 device（不同 CS）

   #### SPI 设备描述（cfg）

   ```
   typedef struct {
       int bus_id;     // 1 表示 SPI1（示例）
       int cs;         // 0/1
       int mode;       // SPI mode
       int max_hz;     // 最大速率
   } spi_cfg_t;
   ```

   #### SPI bus 私有数据（bus_data）

   ```
   typedef struct {
       int controller_id;     // SPI1
       // 寄存器基址 / HAL 句柄 / DMA 等都可以放这里（示例可简化）
   } spi_bus_priv_t;
   ```

   #### SPI device 私有数据（driver_data）

   ```
   typedef struct {
       int cs;
       int mode;
       int max_hz;
   } spi_dev_priv_t;
   ```

   ------

   ### 5.2 SPI 驱动（两个）

   - `spi_flash_driver`：`compatible = "acme,spi-flash"`
   - `spi_lcd_driver`：`compatible = "acme,spi-lcd"`

   **probe() 要做的事：**

   - 从 `dev->cfg(spi_cfg_t)` 读取 CS/mode/max_hz
   - 分配 `spi_dev_priv_t`，写入 `dev->driver_data`
   - 绑定 `dev->ops = spi_dev_ops`

   ------

   ### 5.3 SPI 互斥与统一入口（重点）

   #### SPI device 的 read/write 不直接操作硬件

   `spi_dev_ops->read/write` 内部仅做：

   ```
   bus->ops->configure(bus, dev)
   bus->ops->xfer(bus, dev, tx, rx, len)
   ```

   #### 锁在 bus->xfer 内部（强制一致）

   `spi_bus->ops->xfer` 的语义：

   ```
   if has_lock: lock(bus)
   
   从 dev->driver_data 取得 cs/mode/max_hz
   从 bus->bus_data 取得控制器实例
   执行一次完整 transaction（含 CS 断言/释放）
   
   if has_lock: unlock(bus)
   ```

   > 这与 RTT 的 `rt_spi_bus->ops->xfer` 思想一致：**总线层集中管理互斥与硬件访问**。

   ------

   ## 5.4 UART：挂在 platform_bus（Linux 语义）

   #### platform_bus 特性

   - `name = "platform"`
   - `has_lock = false`
   - `ops = NULL`

   #### UART cfg

   ```
   typedef struct {
       uintptr_t base;
       int irq;
       int baud;
   } uart_cfg_t;
   ```

   #### UART 私有数据（driver_data）

   ```
   typedef struct {
       uintptr_t base;
       int irq;
   } uart_priv_t;
   ```

   #### uart_driver

   - `driver.bus = &platform_bus`
   - `driver.compatible = "acme,uart"`
   - `probe()`：解析 cfg，分配 priv，绑定 `dev->ops = uart_ops`

   > UART 不走 bus->xfer（platform_bus 没有 xfer）。
   >  UART 的并发保护（若需要）属于 UART 自身（设备级锁），不是 platform_bus 的锁。

   ------

   ## 6. match() 规则（简化设备树思想）

   示例采用最小规则：

   - `strcmp(dev->compatible, drv->compatible) == 0` 视为匹配
   - 且要求 `dev->bus == drv->bus`（同一条总线体系内匹配）

   好处：

   - 教学清晰：**设备描述（compatible）决定选择哪个驱动**
   - 接近 Linux 的 “compatible / match_table” 语义（简化版）

   ------

   ## 7. 工程文件建议（OpenCode 友好）

   建议拆 6～8 个文件，便于讲义展示“模块边界”：

   1. `dev.h`：`device_t`、`dev_ops_t`
   2. `bus.h / bus.c`：`bus_t`、`bus_ops_t`、device/driver 注册与匹配、锁接口
   3. `drv.h`：`driver_t`
   4. `spi_bus.c`：`spi_bus_ops{configure,xfer}` + bus_data（模拟控制器）
   5. `spi_flash_drv.c`：flash 驱动 + probe + spi_dev_ops（调用 bus->ops）
   6. `spi_lcd_drv.c`：lcd 驱动 + probe + spi_dev_ops（或复用同一 spi_dev_ops）
   7. `uart_drv.c`：uart 驱动 + probe + uart_ops
   8. `main.c`：初始化两个 bus；注册驱动与设备；演示 read/write

   ------

   ## 8. 讲义中最值得强调的点（最终定版）

   1. **probe 是工厂方法**：匹配成功后才创建/初始化产品实例
   2. **bus 决定匹配规则**：device/driver 分离，动态匹配
   3. **driver_data(user_data) 是实例上下文**：同类驱动支持多个实例
   4. **共享总线互斥集中在 bus->xfer**：避免各驱动“自觉加锁”导致不一致
   5. **platform_bus 统一“片上外设”语义**：Linux 下 UART 不是无总线，而是 platform 逻辑总线
   6. **CS/base/irq 等个性化配置不进入 device 通用字段**：通过 cfg/driver_data 扩展
