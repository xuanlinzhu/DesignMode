## 1. 目标

请实现一个 **基于 C 语言的 Decorator（装饰模式）示例程序**，运行环境按 **类 Linux / POSIX 风格的嵌入式系统** 来设计。

这个示例的核心目标不是做完整日志框架，而是要**清晰展示装饰模式的结构和思想**：

- 所有日志输出对象遵循同一个抽象接口
- 基础对象负责真正写日志
- 装饰器对象也实现同一接口
- 装饰器内部持有一个同接口对象
- 多个装饰器可以递归包裹
- 调用一次写日志接口，会形成多层增强行为叠加

------

## 2. 场景定义

设计一个简化的日志输出系统。

核心行为是：

```
write(log_message)
```

表示把一条日志写到某个输出目标。

本示例只要求一个基础输出目标：

- **文件输出**，使用 **POSIX 文件接口** 完成，例如 `open / write / close`

在基础文件写入能力之上，希望可以动态附加以下增强功能：

- 附加时间戳
- 附加日志级别
- 附加模块名

最终日志格式类似：

```
[2026-03-12 10:15:23] [ERROR] [Sensor] read failed
```

其中：

- 时间戳由一个装饰器附加
- 日志级别由一个装饰器附加
- 模块名由一个装饰器附加
- 真正写入文件由基础写入器完成

------

## 3. 模式要求

必须严格按 **Decorator 模式** 实现，不要写成普通字符串拼接流程，也不要写成继承式组合爆炸。

需要体现以下角色。

------

### 3.1 Component（抽象构件）

定义统一日志写入接口。

建议命名为：

```
LogWriter
```

接口形式建议为一个结构体，内部包含函数指针，例如核心操作：

- `write`
- `destroy`

`write` 表示写入日志
 `destroy` 表示释放对象资源

客户端只能依赖这个抽象接口，而不能直接依赖具体实现类型。

------

### 3.2 ConcreteComponent（具体构件）

实现基础文件写入能力。

建议命名为：

```
FileLogWriter
```

职责：

- 打开日志文件
- 使用 POSIX `write()` 写入日志
- 负责底层文件描述符管理

要求：

- 构造时传入文件路径
- 文件打开方式使用 POSIX 接口
- 追加写入
- 每条日志自动补换行，或者由上层统一组织后传入

------

### 3.3 Decorator（抽象装饰）

也实现 `LogWriter` 接口，同时内部持有一个 `LogWriter*`。

建议命名为：

```
LogWriterDecorator
```

它是所有具体装饰器的公共父结构。

它的核心意义是：

- 自己也是 `LogWriter`
- 内部包着另一个 `LogWriter`

这必须在结构设计中体现出来。

------

### 3.4 ConcreteDecorator（具体装饰）

至少实现以下三个具体装饰器：

- `TimestampDecorator`
- `LevelDecorator`
- `ModuleDecorator`

这些装饰器都要在调用内部 writer 之前，对日志消息进行增强，然后再转发给下一层。

------

## 4. 功能要求

------

### 4.1 FileLogWriter

职责：

- 使用 POSIX 接口写文件
- 真正完成日志落盘

要求：

- 文件打开使用 `open`
- 写入使用 `write`
- 关闭使用 `close`
- 打开模式为追加写
- 具备基本错误处理
- 写入接口返回状态码，便于上层判断成功失败

不需要实现复杂缓冲、文件滚动、多线程安全。

------

### 4.2 TimestampDecorator

职责：

- 在日志前增加时间戳

格式要求尽量清晰，例如：

```
[2026-03-12 10:15:23]
```

时间获取可以用标准/POSIX 风格时间接口，例如：

- `time`
- `localtime_r`
- `strftime`

最终效果示例：

```
[2026-03-12 10:15:23] message
```

------

### 4.3 LevelDecorator

职责：

- 在日志前增加日志级别

建议支持以下级别：

- INFO
- WARN
- ERROR

要求：

- 级别在创建装饰器时指定
- 每个装饰器实例固定一个 level 即可
- 不要求设计复杂动态等级系统

最终效果示例：

```
[ERROR] message
```

------

### 4.4 ModuleDecorator

职责：

- 在日志前增加模块名

例如：

```
[Sensor] message
```

要求：

- 模块名在创建装饰器时传入
- 模块名作为装饰器内部状态保存

------

## 5. 装饰链要求

程序必须展示 **多层装饰器嵌套**，明确体现行为叠加。

至少展示以下组合：

------

### 示例 1

组合结构：

```
Timestamp(Level(Module(FileLogWriter)))
```

调用：

```
write("read failed")
```

输出到文件的内容类似：

```
[2026-03-12 10:15:23] [ERROR] [Sensor] read failed
```

------

### 示例 2

组合结构：

```
Level(Timestamp(FileLogWriter))
```

调用两次不同日志，展示可以替换装饰顺序和组合方式。

------

## 6. 实现约束

------

### 6.1 必须使用 C 语言

要求：

- 使用 C99 或 C11
- 不要使用 C++
- 不要使用面向对象语法糖
- 通过结构体 + 函数指针模拟抽象接口

------

### 6.2 必须体现装饰模式结构

代码中必须清楚体现：

- 统一接口
- 具体构件
- 抽象装饰器
- 具体装饰器
- 装饰链组合

不能只是写成几个处理函数串起来。

------

### 6.3 文件接口必须使用 POSIX API

必须使用：

- `open`
- `write`
- `close`

可根据需要使用：

- `fsync`
- `snprintf`
- `time`
- `localtime_r`
- `strftime`

不要使用 `fopen / fprintf / fclose` 这类 stdio 文件接口。

------

### 6.4 内存管理要求

可以使用动态内存分配，但要简单清晰。

要求：

- 每个对象有明确的 create/init 和 destroy
- destroy 时正确释放装饰链资源
- 不要产生内存泄漏
- ownership 要明确：最外层 destroy 后应能递归释放内部对象，或者明确说明释放策略

------

### 6.5 错误处理

需要有基本错误处理：

- 文件打开失败
- 写入失败
- 参数为空
- 缓冲区长度不足

错误处理不需要做得很复杂，但不能完全忽略。

------

## 7. 代码组织要求

建议拆分为多个文件，结构清晰。

建议至少包含：

- `log_writer.h`
- `file_log_writer.c`
- `log_decorator.h`
- `timestamp_decorator.c`
- `level_decorator.c`
- `module_decorator.c`
- `main.c`

如果 OPENCODE 觉得文件太多，也可以适当合并，但必须保证层次清晰。

------

## 8. 接口设计建议

这里只给方向，不要求完全照抄，但结构必须体现模式。

------

### 8.1 抽象接口

统一日志接口建议包含：

- `int (*write)(LogWriter *self, const char *message);`
- `void (*destroy)(LogWriter *self);`

其中：

- `write` 返回 0 或负值表示结果
- `destroy` 负责释放对象

------

### 8.2 抽象装饰器

抽象装饰器内部应至少包含：

- 一个基础 `LogWriter` 接口对象
- 一个被包装的 `LogWriter *wrapped`

这部分必须明显体现“自己也是组件，同时拥有一个组件”。

------

### 8.3 具体装饰器处理方式

每个具体装饰器的逻辑都应是：

1. 接收原始 message
2. 生成增强后的 message
3. 调用内部 `wrapped->write(...)`

注意这里的 message 增强要尽量安全：

- 使用固定长度缓冲区
- 使用 `snprintf`
- 防止溢出

------

## 9. main 函数演示要求

`main()` 中必须明确展示 Decorator 的使用方式。

要求包含：

------

### 9.1 创建基础对象

创建一个 `FileLogWriter`，输出文件例如：

```
app.log
```

------

### 9.2 创建装饰链

例如：

```
FileLogWriter
↓
ModuleDecorator("Sensor")
↓
LevelDecorator(ERROR)
↓
TimestampDecorator
```

注意对外暴露的最终对象仍然是 `LogWriter *`。

------

### 9.3 写日志

至少写两到三条日志，内容不同，便于观察结果。

------

### 9.4 展示另一种组合

再构建另一条较简单的装饰链，证明装饰器可以自由组合。

------

## 10. 输出效果要求

程序运行后，生成日志文件 `app.log`，内容类似：

```
[2026-03-12 10:15:23] [ERROR] [Sensor] read failed
[2026-03-12 10:15:24] [ERROR] [Sensor] init timeout
[INFO] [2026-03-12 10:15:25] logger started
```

顺序可以根据组合不同而变化，但应能明显看出：

- 时间戳来自一个装饰器
- 级别来自一个装饰器
- 模块名来自一个装饰器
- 底层写文件来自基础 writer

------

## 11. 代码注释要求

代码中请适量注释，明确说明：

- 哪个结构是 Component
- 哪个结构是 ConcreteComponent
- 哪个结构是 Decorator
- 哪个结构是 ConcreteDecorator
- 哪部分体现了装饰链组合
- 为什么这属于 Decorator，而不是 Builder 或 Strategy

注释不要过度，但要有教学价值。

------

## 12. 不要这样实现

请避免以下错误实现方式。

------

### 12.1 不要写成普通工具函数流水线

例如：

```
add_timestamp(buf);
add_level(buf);
add_module(buf);
write_file(buf);
```

这种只是顺序处理，不足以体现 Decorator 的对象结构。

------

### 12.2 不要写成大量组合类型

例如：

- `TimestampFileWriter`
- `LevelFileWriter`
- `TimestampLevelFileWriter`

这会退化成继承/类型爆炸思路。

------

### 12.3 不要把所有格式拼装逻辑都塞到 FileLogWriter

否则基础构件就不再“单一职责”了。

------

### 12.4 不要做成 Strategy

例如不要把 `level/module/timestamp` 做成简单配置开关：

```
writer->enable_timestamp = 1;
writer->enable_level = 1;
```

这样会弱化 Decorator 的结构特征。
