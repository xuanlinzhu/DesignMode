## 1. 任务目标（必须满足）

实现一个基于 C 语言的命令模式示例，用于模拟：

> **通信线程接收外部控制请求，将请求封装为命令对象并投入命令队列；执行线程从队列中取出命令并执行，从而避免通信线程被耗时操作阻塞。**

必须体现：

- 请求被封装为**命令对象**
- 通信线程只负责：
  - 接收输入
  - 解析输入
  - 创建命令
  - 投递命令到队列
- 执行线程只负责：
  - 从队列取命令
  - 调用命令执行接口
- 不允许通信线程直接操作设备模块
- 必须体现**发送者**与**执行者**解耦
- 必须体现**命令队列**的存在价值

------

## 2. 核心场景（必须按此实现）

系统中存在两个线程角色：

### 2.1 通信线程

负责接收模拟外部报文，例如：

```text
LED_ON
LED_OFF
MOTOR_SET 120
SAVE_CONFIG 3
```

通信线程行为必须是：

```text
接收报文
-> 解析命令类型和参数
-> 创建对应命令对象
-> 推入命令队列
-> 立即返回继续处理下一条报文
```

通信线程**不能**直接调用：

- `led_on()`
- `motor_set_speed()`
- `save_config()`

------

### 2.2 执行线程

负责不断从命令队列中取命令并执行：

```text
从队列取出命令
-> 调用命令 execute()
-> 命令内部调用接收者模块
-> 释放命令对象
```

------

## 3. 模式角色（必须清晰）

代码中必须体现以下角色：

### 3.1 Command

抽象命令接口，所有具体命令必须实现统一执行接口。

### 3.2 ConcreteCommand

至少实现以下具体命令：

- `LedOnCommand`
- `LedOffCommand`
- `MotorSetSpeedCommand`
- `SaveConfigCommand`

### 3.3 Receiver

真正执行动作的模块，至少包括：

- `LedReceiver`
- `MotorReceiver`
- `ConfigReceiver`

### 3.4 Invoker

命令队列，负责保存待执行命令。

### 3.5 Client

通信线程，负责创建具体命令并投递到队列。

------

## 4. 抽象命令接口（必须这样设计）

必须定义统一命令基类：

```c
typedef struct command
{
    void (*execute)(struct command *self);
    void (*destroy)(struct command *self);
} command_t;
```

说明：

- `execute`：执行命令
- `destroy`：销毁命令对象，释放资源

禁止把所有命令逻辑塞进一个大 `switch-case` 里统一执行。
必须通过函数指针体现“不同命令对象具有不同执行行为”。

------

## 7. 命令队列（必须存在，不能省略）

必须实现一个独立的命令队列模块。

禁止直接在通信线程里调用命令执行函数。
必须满足：

- 队列元素类型为 `command_t *`
- 支持：
  - 初始化
  - 入队
  - 出队
  - 判空
  - 判满（如果使用固定容量）

建议使用循环队列。

建议接口：

```c
void command_queue_init(command_queue_t *q);
int command_queue_push(command_queue_t *q, command_t *cmd);
command_t *command_queue_pop(command_queue_t *q);
int command_queue_is_empty(command_queue_t *q);
```

## 8. 双线程表达方式（按简化模型实现）

本示例主要用于表达模式思想，不要求使用真实 RTOS 线程。

必须采用“模拟双线程”的写法：

- `comm_thread_step()`：模拟通信线程处理一步
- `worker_thread_step()`：模拟执行线程处理一步

例如：

```c
void comm_thread_step(...);
void worker_thread_step(...);
```

主函数中通过交替调用这两个函数，表达“两条线程并行协作”的效果。

## 10. 日志输出要求（必须有）

必须通过日志证明：

- 通信线程没有直接执行设备动作
- 执行线程异步执行命令
- 队列确实在中间起作用

建议输出风格如下：

```text
[Comm] recv: LED_ON
[Comm] create: LedOnCommand
[Comm] push queue

[Worker] pop command: LedOnCommand
[Receiver] LED ON
```

对于耗时命令必须体现：

```text
[Comm] recv: SAVE_CONFIG 3
[Comm] create: SaveConfigCommand
[Comm] push queue
[Comm] recv: LED_OFF
[Comm] create: LedOffCommand
[Comm] push queue

[Worker] pop command: SaveConfigCommand
[Receiver] save config start: 3
[Receiver] save config done: 3

[Worker] pop command: LedOffCommand
[Receiver] LED OFF
```

重点是要从日志看出：

> `SAVE_CONFIG` 很耗时，但通信线程仍然能继续接收后续报文。

## 12. 关键设计约束（非常重要）

------

### 12.1 必须用“命令对象”

禁止写成：

```c
if (strcmp(msg, "LED_ON") == 0) {
    led_on();
}
```

这不是命令模式。

------

### 12.2 必须有抽象命令接口

禁止直接把命令当作普通数据结构，然后在 worker 线程里再写一个大 `switch-case` 统一执行所有动作。

错误示例：

```c
switch (cmd->type)
{
    case CMD_LED_ON: ...
    case CMD_LED_OFF: ...
    case CMD_SAVE_CONFIG: ...
}
```

这个会退化为“命令枚举 + 分发器”，不符合本示例的重点。

------

### 12.3 必须让命令持有接收者

具体命令对象内部必须持有对应 receiver 指针。
执行时由命令调用 receiver。

------

### 12.4 通信线程不能直接依赖接收者行为

通信线程只负责创建命令，不负责执行动作。

------

### 12.5 SaveConfigCommand必须表现出“耗时”

否则“双线程队列避免阻塞通信线程”的价值不明显。
